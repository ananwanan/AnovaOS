# M17.5 图形开发验收

[English](../../en/validation/M17.5.md) | **简体中文**

## 复现

```sh
cargo xtask fetch
cargo xtask toolchain-build
cargo xtask rust-build
cargo xtask desktop-monitor-test
cargo xtask desktop-workflow-test
cargo xtask desktop-build-test
cargo xtask desktop-files-fault-test
```

声明配置使用 QEMU q35/TCG、单 BSP、3 GiB RAM、OVMF、800×600 VGA、PS/2 输入、
独立 COM1 记录和每种配方一个全新 Linux personality JBD2 盘。重启使用同一个盘。
C 保留 35 秒构建上限，新 C++、Rust 配方为 120 秒构建和 600 秒每启动看门狗，
继续以 500 毫秒观察编译完成。交互上限为 5 秒。资源数字来自调度点的分配器计数，
逐进程内存和 CPU 精确占用不可用。
编译测试上限为已分配内核堆 12 MiB、额外 131,072 个 4 KiB 页、32 个占用任务槽、
单进程 32 个 FD 和 2,048 个 VFS 槽。运行时采用 16 MiB 堆、四组 PTY、
四个 GUI 预留和一个活动构建。

观察者以物理 QMP 输入录入源码、在 Files 保存、由启动器构建、在图形终端运行 guest
产物并通过服务页关机。串口命令独立核对源码字节并检验 COM1。暂停磁盘副本保存
各阶段观察，`debugfs` 与 `e2fsck -f -n` 独立检查。宿主路径及原始记录位于
`build/desktop-workflow-test/` 的各时间戳目录。固定配方及发布边界见
[工作流程契约](../milestones/M17_WORKFLOW.md)。

编译期间的观测要求在指定编译器首进程退出前，取得新按键的实际画面回显与 COM1 状态。
取消直接作用于存活的首进程，随后通过独立 GUI 输入和 COM1 验证取消恢复。
C 压力用例在 GCC 运行时由图形终端持有十八个真实 Linux 子进程，再等待它们实际释放。
原有长输出门禁另行验证 220,000 字节输出期间的实际 GUI 及 COM1 输入。

发布故障用例从已验证的 C 工作盘制作各自的副本，在图形界面保存不同的源码。
编译器真实零退出后，QEMU 在写入持久暂存文件时注入一次设备写入或 flush 失败。
观察者逐字节比较停止镜像中的旧 ELF，经过 guest 普通恢复挂载后运行旧程序，清理遗留暂存
路径，再重试并核验新程序的字节和退出状态。

## 本地结果

2026-11-14，运行 `1794629185306963286` 在 Ubuntu 24.04 WSL2、QEMU 8.2.2 和
Rust 1.90.0 环境完成三种语言的六次启动。GCC 和 G++ 为锁定的源码构建 11.2.0 工具。
C++ 使用两个翻译单元、`std::string`、`std::vector`、RAII 和实际的 C++ 运行库。
Rust 使用经过校验的上游 rustc、匹配的 musl std 和 guest 链接器。三种源码均在
AnovaOS 内录入并编译。

重启前后 C 均打印 `C-ANSWER-42`，C++ 打印 `CPP-42` 和 `RAII`，Rust 打印
`RUST-42`。每组正常关机与重启的源码和 ELF 逐字节一致。三个取消用例均报告信号 15。
C 压力用例持有额外十八个 Linux 子进程，构建耗时 1,892 毫秒，按键至画面 64 毫秒，
COM1 为 241 毫秒。每次关闭均回收带标签的构建家族，并清除健康挂载上的易失和持久
暂存文件。完整 SHA-256 保留在运行记录中。
独立 C++、Rust 取消复测在向存活编译器发送停止前观察了两个通道。C++ 的窗口画面和
COM1 分别为 65 和 225 毫秒，Rust 分别为 64 和 806 毫秒。两轮同时保留取消后的
GUI 响应、信号状态和逐字节一致的重启旧产物。

两个发布故障用例也通过，完整门禁共十次启动。编译器首先以零退出，随后 virtio 写入
或 flush 返回状态 1。启动器显示 `published=false error=-21`，回收家族并删除易失输出。
两次 COM1 分别为 141/151 毫秒。两次恢复启动均重新运行旧 ELF，输出 `C-ANSWER-42`
并以 7 退出，随后重试发布另一程序并以 19 退出。恢复盘通过独立 e2fsck。
原始发布及恢复 UART/QMP、窗口与重启画面、采样以及源码和产物散列见
[可移植证据](../../assets/validation/M17_WORKFLOW_LOCAL.json)。

早期失败保留。PM 定时器将首次编译负载交互超时定位到重复的同步 JBD2 写入。
一次链接器 writev 耗时 2,120 毫秒，后续数次为 434–585 毫秒。易失链接输出和 64 KiB
分段发布减少提交次数，终端按行上传减少单个回显字符的画面更新工作。早期 C 观察者在
shell 中留下探测字母，产生实际退出码 127。修正后运行产物前删除该字母。QMP 一次发送
关机键的按下及释放，并要求实际干净关机标记和 QEMU 正常退出。
后续两次观测发现合成器指针遮挡提示符，以及终端仍有焦点时会收到启动器关机步骤。
最终门禁将指针移出文字区域、检查新回显，并在关机前将焦点切回启动器。

## 相关回归

声明配置在 guest 内保留真实 virtio 与 JBD2。成功的工作流程、Files 故障和 M16 存储
复测使用宿主内存文件系统上的普通镜像文件。早期 WSL 磁盘文件运行出现实际的
2,000 毫秒 virtio FLUSH 超时及一次超过 5 秒的 Files 保存。复测沿用原超时、
writeback 模式、guest 持久化检查与独立 QEMU 启动，验证宿主保持运行时的指定设备
故障与 QEMU 重启恢复。

`desktop-build-test` 保留 0x104 回归，并验证 0x106 的错误用户地址、结果保留、
所有者和旧身份、脱离会话家族取消、暂存身份替换拒绝、发布准入。真实长输出达到
220,000 字节，保留 8 KiB 尾部，其他窗口从按键至画面验证在 2,956 毫秒内，COM1 为
60 毫秒。任务、FD、全局打开描述及 PTY 按原上限耗尽。Files 独立故障门禁沿用原
存储与延迟断言，完成全部 16 用例和 43 次启动。

## 边界

监控和早期桌面配置覆盖真实客户端及合成器故障。编译使用固定配方和原有 tmpfs 单文件
1 MiB 上限。PM 硬件计数仍观测到一次 Rust `munmap` 为 2,420 毫秒。GUI 数字为各工作负载
内离散探测，COM1 数字包含宿主观察者调度及轮询。M16 远端 CI、硬件、任意断电、
M18 编译器重建和纯 guest 镜像生成分别验收。

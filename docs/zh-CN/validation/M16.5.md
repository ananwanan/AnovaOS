# M16.5：JBD2 日志与崩溃恢复

[English](../../en/validation/M16.5.md) | **简体中文**

2026-10-27（Asia/Shanghai）在 `feat/m16-foundation`、基线 `e963c01` 实现并本地验收。
扩展 [M16.4](M16.4.md)，保留无日志配置和独立 ext2 路线；远端 CI 单独记录。
格式实现依据公开的 [JBD2 说明](https://www.kernel.org/doc/html/latest/filesystems/ext4/journal.html)，
没有引入 Linux 内核实现代码。

## 准入配置

`ext4-jbd2-v1` 保留现有 4 KiB blocks、256-byte inodes、线性目录、root 归属及严格分配/
命名空间审计。增加 COMPAT `has_journal`（4）、内置保留 inode 8 和 INCOMPAT recovery（4）。
外部日志、64-bit/flex/ext4 元数据校验和、fast/async commits、任意 Linux 日志历史、环形/
回绕的未完成日志及多个并行未 checkpoint 事务不在本配置内；不支持的组合在恢复写入前拒绝。

不可变日志映射必须能放入 inline extent root（最多四段），包含 1,024–8,192 个 4 KiB blocks，
没有重复或与保留块冲突的归属。JBD2 v2 superblock 使用大端字段、匹配 UUID、单一用户，
abort errno 必须为零。记录使用 CRC32C checksum-v3、32-bit 目标、UUID tags、数据转义、
descriptor/commit 校验和；superblock 校验覆盖前 1,024 字节。干净且空的 mkfs 无校验和日志
在首次事务中升级；拒绝活跃的无校验和日志。未完成日志从逻辑块 1 开始；写入前拒绝序号回绕到零。

每事务最多暂存 1,024 个变化的文件系统块，连同 descriptor/commit 必须能放入日志。所有分配
均可失败，设备发布阶段不再分配。新工作盘采用 2,048-block 日志；更小日志可能对大单次事务
返回 `NO_MEMORY`，仍可分次小块写入。堆、节点、task/fd 和映射限额不变。干净日志盘可以只读
挂载；需恢复的盘必须使用显式可写路线，不会在只读挂载时暗中重放。

## 持久性与恢复契约

采用同步 **data=journal**：所有暂存的数据和元数据均经过日志，对覆盖写的数据保证强于仅记录
元数据的 ordered 模式。一次后端操作是一个事务，多 syscall 的应用序列不会自动成为同一事务。
成功修改已完成 checkpoint/退役；`fsync`/`sync` 刷新整个挂载，rename 包含其元数据 commit。
应用可写入/fsync 临时文件，再 rename 替换。

1. 持久化并 flush ext4 recovery bit，同时保留 ext4 valid-state bit。
2. 写入并 flush 带事务序号的活跃日志 superblock。
3. 写 descriptor 与转义数据，flush 完整日志体。
4. 写带校验和的 commit 并 flush，之后才允许修改 home 地址。
5. 写全部 home blocks 并 flush checkpoint。
6. 日志头退役并 flush，之后才允许复用空间。

发布阶段任一 write/flush 失败会使当前挂载停止服务，sync/shutdown 返回失败。返回失败的操作
可能已经提交；重启后允许的结果是完整前态或完整后态，不能因此报告干净。成功关机必须先回收
全部孤儿并完成日志退役，再清 recovery bit；设备故障可能阻止尽力修复标记。

重放先查找匹配且校验正确的 commit；忽略没有 commit 的前缀，拒绝已提交 descriptor/数据/
commit 的损坏，不发布未完整验证的重放。恢复 overlay 必须通过不可变几何、唯一块归属、空闲
计数、根目录链和链接/孤儿审计。恢复中再次崩溃可重复 checkpoint。有界 revoke 读取器跳过
已撤销目标；写入器在任何后续块复用前完成全部 checkpoint，因此无需生成 revoke 记录。

unlink/替换将经典 `s_last_orphan`/inode `i_dtime` 链与命名空间改变一同提交。运行时打开句柄/
映射保留身份；重启后这些句柄已不存在，在归属审计后通过后续日志事务回收每个孤儿，不会因未
恢复 orphan 链而静默泄漏或复用活跃 inode。

## 实际本地验收

```sh
cargo xtask foundation-journal-test
cargo test --locked -p anova-storage --test journal
```

五个宿主测试使用真实 e2fsprogs 1.47.0 镜像。矩阵在创建、覆盖、截断、rename、unlink、最终
回收中执行 **1,740** 个中断场景：write-through 扇区、flush 前丢失易失缓存，以及失败 512-byte
写入仅持久化前 256 字节。每个恢复后停止盘均通过独立 `e2fsck -fn` 与命名空间/数据检查。
另覆盖恢复的每次 write/flush 再中断，descriptor/数据/commit 校验和损坏无写入拒绝，300 个数据
块的多 descriptor 和 magic 转义，以及在相同失败副本上对比本实现与 `e2fsck -fy` 的 revoke/
重放。十二次连续真实分配失败验证日志预检回滚及重试。这是声明的扇区/撕裂模型，不是任意实机
故障覆盖。

`build/journal-host/` 保留基线、准确扇区字节/事件轨迹、结果和各类原始失败盘。任一矩阵场景均
可重建，不修改原盘：

```sh
python3 scripts/reconstruct_journal_cut.py   build/journal-host/matrix/write-baseline.ext4   build/journal-host/matrix/write-events.txt 25 build/disks/cut.ext4 --cache
```

`--tear` 重现失败半扇区前缀；cut 从零计数。门禁还运行真实单 BSP q35/TCG/OVMF、1 GiB RAM、
virtio-blk guest：完整 Linux/musl 写入套件、sync、持久标记、强制终止 QEMU、恢复启动、精确
元数据和干净 ACPI 关机。恢复前保留原始非正常停止盘。pending-commit 逐写点矩阵由宿主驱动，
guest 的中断位于 sync/checkpoint 后；既有 M16.4 virtio 读/写/flush 错误门禁仍单独保留。

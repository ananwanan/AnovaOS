## 限制与当时下一步

仅接受 BSP 异常/计时器基线。所有外部 IRQ 保持屏蔽，routing override、NMI 和外设投递未测试；IST3 已安装，但未实际验证 NMI/machine-check 投递。时间为粗粒度已投递 IRQ 计数，IF=0 期间可滞后。该阶段不回收内存，也没有分配器、用户进程或调度。M3 须先建立明确内存所有权，再替换保留引导栈/页表、加入 frame allocator 和 heap。见 [M2_CPU](../milestones/M2_CPU.md)。

## 固件 I/O APIC 编号后续修复（2026-11-14）

本节独立于上方 2026-10-21 的历史证据。源码基线为 `dev` 的
`648a99ff95f1ee50759d859310461b6593d64a28`，修复分支为 `feat/fix-ioapic-boot`。
用户提供的 `boot.log` 在 `MADT/I/O APIC identity mismatch` 处停止：寄存器编号为 0，
固件编号为 128。本次验证没有重新运行原虚拟机。

修复通过已校验的 MADT 物理地址访问各控制器。只有所有重定向屏蔽位读回成功后，才报告
两个编号、地址及 `id_mismatch`。控制器编号寄存器不变；LAPIC/BSP 身份、固件拓扑/地址
准入、GSI 范围/溢出拒绝与 IF=0 串行访问均保留。外部 IRQ 仍全部屏蔽，实际外部中断的
编程与路由需要单独验收。

新增 `cargo xtask smoke --case ioapic-id-mismatch` 选择互斥的 QEMU 测试特性，在正常
ACPI 校验后仅把解析后的首个 MADT 编号从 0 改成 128。控制器地址、GSI 拓扑、真实 MMIO
及逐引脚屏蔽操作不变。门禁要求实际到达注入点、`0xfec00000` 的寄存器编号为 0、GSI 为
`0..24`、BSP 目标为 0、`all_masked=true`、`id_mismatch=true`、完整正常冒烟检查及 QEMU
退出码 33。`verify` 保留原有 13 项并增加此第 14 项。宿主负例拒绝缺失注入、错误编号/
地址/范围/目标、缺屏蔽/定时器/完成证据、错误退出与超时；同时接受 LF 和真实 UART CRLF。

初次测试框架尝试使用 QEMU `-acpitable`，它追加了第二个 MADT，正确触发 `Duplicate MADT`，
此保护保持不变。最终的解析后拓扑注入在修复前复现原断言：`left: 0`、`right: 128`，
QEMU 退出 35，冒烟命令退出 1。失败测试 ISO 的 SHA-256 为
`89f8cc7b48b8533e0b01af8002280aaeca2a50bd8caa2d39fb42880d52a29fac`。
两次尝试的日志分别保留，失败记录不计为验收通过。

本地宿主为 WSL2 下的 Ubuntu 24.04，Rust/Cargo 1.90.0、QEMU 8.2.2，使用锁定的
OVMF/Limine 输入、q35/TCG、一个 vCPU、256 MiB。`cargo xtask doctor` 通过。
宿主严格 Clippy（`xtask`、`anova-platform`，全部 target）及内核普通、
`test-ioapic-id-mismatch`、`desktop-test` 三种独立配置的严格 Clippy 均通过。

`cargo xtask test-host` 的 271 项测试全部通过（含 65 项 xtask 测试）。组合启用
`test-ioapic-id-mismatch,test-panic` 在编译时按要求以 `Select only one boot injection feature`

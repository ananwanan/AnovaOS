## 实际 guest 评估

bootstrap-rust-test 两 QEMU 8.2.2 q35/TCG、one CPU、3 GiB、no NIC，独立 Linux16MiB/512-inode work disk。两 clean ACPI/flush/ack DMA 重置、两 e2fsck 过。build/logs/bootstrap-rust.result.json 嵌 audit/prepared，逐日志 prefixes bootstrap-rust-probe/reboot。

首启动记继承的 Rust/Cargo 版本，guest rustc 编第一方 std/vector/worker-thread/persistent-I/O app 得 42；guest G++ 另编 C++17 fold/std::optional 得 42。宿主停盘解析两 ELF/executable 模式。仅 seed applications，不是编译器组件。

guest 先复制 working Rust ELF，再向同输出编坏 bad.rs，compiler1/真实 expected-expression 诊断，宿主 saved/retained ELF byte-identical。负例/压力后两 apps 仍运行。

宿主诊断对 python3/cmake/ninja/git/perl/pkg-config 真 execvp，各 ENOENT 经检查的 pipe/127；`python3 rust-x.py --help` 原入口 interpreter 无法执行，因此 upstream Python/后续 bootstrap 未运行。缺 optional tools 仅配置证据，不推每 route 必需六者。

Cargo 用独立最小清单 curl = "=0.4.48"，与 upstream manifest/lock 匹配；/rs/vendor 缺依赖，返回 101/真实缺少 curl+vendor path，有界输出验后存 build/logs/bootstrap-rust-cargo-dependency.log。未在 guest 配置/构建完整 Cargo workspace/release vendor。

容量 >1 MiB EFBIG/旧字节、EMFILE 恢复、EAGAIN/reap/new wait；第二次启动再运行两 app，31 workspace files（upstream/notices/fixtures/Cargo output/ELFs/saved 复制）全部相同。

# M18.3: guest boot-image construction evidence

**English** | [简体中文](../../zh-CN/validation/M18.3.md)

The bounded UEFI optical profile passed six QEMU boots on 2026-11-21, from
13:03:14 to 13:09:50 in Asia/Shanghai. Two independent clean JBD2 disks produced
byte-identical final images. Both images started the exact previously guest-built
kernel and the native COM1 workflow. The [image contract](../milestones/M18_BOOTSTRAP.md#guest-construction-of-the-boot-image)
describes the format and the separate acceptance for GUI-enabled kernels and compiler reconstruction.

## Inputs, command and budgets

Run `cargo xtask m18-image-test REPORT GUEST_ELF` with the accepted capacity result
and its preserved kernel. `cargo xtask foundation-capacity-test` generates a new
pair when necessary. The executed run used the historical [M17 capacity replay](M17.5.md#related-regressions).
The gate checked the replay receipt, the original kernel construction and recovery
UART logs, and the exact kernel file on the stopped ext4 work disk. The imported
431,488-byte ELF uses target `x86_64-unknown-none` and features
`ext4-write,bootstrap-metrics`. Its original guest build inherited Rust/Cargo/rust-lld
1.90.0 and matching target libraries.

The host built the static musl image writer, native applications and base
`anova.initramfs.v1`, and prepared the separate initial boot seed. The guest writer
consumed 19 regular inputs totaling 25,544,624 bytes. The largest was the 12,261,097-byte
initramfs. The Limine 9.5.0 UEFI executable, EFI CD image and license used the
[boot lock](../../../boot/dependencies.toml). The guest wrote the final ECMA-119 optical
image with Rock Ridge names and a UEFI El Torito entry. Host xorriso read-only extraction
then independently compared every input byte, including `/boot/kernel.elf`.
[ECMA-119](https://ecma-international.org/publications-and-standards/standards/ecma-119/),
[UEFI 2.10 optical-media boot](https://uefi.org/specs/UEFI/2.10/13_Protocols_Media_Access.html#iso-9660-and-el-torito),
[El Torito 1.0](https://www.scs.stanford.edu/nyu/04fa/lab/boot-cdrom.pdf).

The declared machine was q35/TCG, OVMF, 256 MiB RAM, one BSP and no network.
The two fresh work disks were 64 MiB JBD2 ext4 with 4 KiB blocks and 4,096 inodes.
The writer's limits were 16 MiB per input, 32 MiB per image and a 4 KiB streaming chunk.
The run enforced the existing 16 MiB heap, 2,048 VFS slots, 32 occupied task slots
and 32 FDs per process, plus 32,768 additional 4 KiB frames, 600 seconds per
construction/pressure boot, 90 seconds per final-image boot and 5,000 ms for the
observed COM1 cancellation response.

## Independent host checks

`python3 ports/bootstrap/test_image_build.py` passed six tests under WSL. The
host-built static musl writer produced
equal synthetic-input images twice. `xorriso` independently extracted their exact files and
reported the UEFI El Torito entry. The test suite checked the catalog checksum and exact
boot-image payload and exercised missing/symlinked/special/oversized input, candidate
collision and cleanup, publication blocked by a directory, output limit failure and an
output alias of the input. The synthetic ELF belongs to this host fixture. A separate
preflight rejected a real guest ELF paired with a different capacity result.

## Guest sessions and recovery

The first construction run exercised real `ENOENT` on a missing input, `EISDIR`
from rename after the full candidate was streamed, and Ctrl+C against the live
writer with signal 2/status 130. Explicit cleanup removed the abandoned candidate.
COM1 returned to the prompt in 21 ms. Both independent final-image boots reported
the exact embedded identity, read persisted user bytes, ran the native C app with
exit 7 and completed clean shutdown. The two extracted ISO trees exactly matched all inputs.

For allocation pressure, the host copied the first stopped work disk and seeded a
31,752,192-byte reserve file, leaving 64 free blocks. The next guest image stream
hit actual `ENOSPC` at 16,384 allocated blocks and removed the failed candidate.
The stopped volume retained the prior ISO and user data byte-for-byte. Booting that
ISO again read the same user bytes, removed the reserve and successfully allocated
a new file. The recovered volume contained 8,569 allocated blocks. Independent
`e2fsck -f -n` passed on all six stopped-session disks.

## Actual hardware profile

`cargo xtask gpu-test` completed with `result=Ok` for three independent boots:

| Boot | Actual behavior |
| --- | --- |
| `gpu-virgl` | Hardware clear/readback, real lost-doorbell watchdog/reset, CPU fallback and successful subsequent GPU reuse |
| `gpu-two-dimensional` | Device lacks VIRGL; actual CPU fallback, unchanged recovery display and serial shell |
| `gpu-absent` | No GPU; actual CPU fallback, unchanged recovery display and serial shell |

The hardware boot reads the actual device's capset-2 renderer:

```text
[GPU:RENDERER] name=D3D12 (NVIDIA GeForce RTX 4060 Ti)
```

The gate rejects software and unknown renderer identities. A separate EGL probe
initially selected LLVMpipe; that did not count as hardware evidence. The passing
QEMU child uses WSLg/Wayland, `GALLIUM_DRIVER=d3d12`, `GDK_BACKEND=wayland` and
`-display gtk,gl=on -vga std -device virtio-gpu-gl-pci`. The guest itself runs
on q35/TCG, `qemu64,+rdrand`, 256 MiB and one BSP, with locked Limine/OVMF and
a temporary ext2 disk. The GPU is secondary and renders offscreen.

## Rendering, boundaries and failure evidence

Each healthy hardware phase checks a 7×5 `0x1280fe` clear with an unchanged
output-tail canary, followed by four 64×64 red, blue, white and green clears.
Both kernel and user compositor check every returned pixel. All four backing
pages start with distinct per-pixel poison; no CPU reference upload supplies
the result. Actual `SUBMIT_3D` and fenced `TRANSFER_FROM_HOST_3D` completions
precede readback checks. The full sequence repeats after the timeout/reset,
giving ten successful hardware render/readback calls and 32,838 compared pixels.

The authenticated-operation negatives cover pre-bind authorization, zero,
oversized and overflowing dimensions, invalid color/reserved fields, a bad
writable output pointer and incorrect request size. Rejected calls leave the
output sentinel unchanged. A real invalid capset request returns `0x1205` from
the device; successful commands validate returned lengths, context and fence.

The failure diagnostic publishes a real request while suppressing its doorbell.
The passing log records:

```text
[GPU:INJECT] lost_doorbell=true published=true
[GPU:TIMEOUT] watchdog=pm-timer deadline_ms=2000 reset_required=true reason=pm-timer elapsed_pm_ticks=7159195
[GPU:RESET] acknowledged=true dma_released=true
[GPU:RECLAIM] frames_restored=true heap_restored=true
[GPU:USER-FAILURE] timeout=true fallback=cpu
```

The host gate requires calibrated PM expiry, not merely the independent
iteration cap. It verifies CPU presentation after the timeout and then launches
a new compositor that again produces checked hardware output. Every successful
device operation resets the device before freeing all DMA; frame and heap counts
return to their exact entry values. The unacknowledged-reset quarantine policy
is implemented and reviewed, but this gate does not induce a reset refusal.

Five actual 800×600 QMP screenshots compare every pixel against the independent
CPU background plus the green tile at `(16,16)`: hardware output, post-timeout
CPU output, recovered hardware output, 2D-only fallback and absent-device fallback.
Each has SHA-256
`69803279e6f5df7617eecfe387fe759eb63f31165953ebce62fe6ce6831104f8`.
This is 2,400,000 complete scanout pixel comparisons. The admitted compositor's
actual PID must exit with status 0 after its completion record and before the
next shell prompt. Every boot requires a real COM1 echo and clean ACPI shutdown
with QEMU exit 0.

An initial host-gate check incorrectly expected the scripted shell's status
marker during an ordinary interactive session. It was corrected to correlate
the actual compositor PID and successful process exit; a host regression test
covers the observed transcript and wrong-PID/fault/nonzero/prompt-order negatives.
The current complete gate passed after that correction.

## Measured latency and artifacts

Ten measured `SUBMIT_3D` plus fenced readback intervals range from **11.852 to
14.728 ms**, with a **12.444 ms median**, using the 3,579,545 Hz ACPI PM counter.
They exclude device negotiation, context/resource/backing setup, reset, usercopy
and final VGA copying. They are small-operation latency observations under TCG
and WSLg, not a throughput benchmark or evidence of a desktop speedup.

Primary artifacts are in `build/gpu/`:

- `gpu-test.result.txt` and `gpu-fallback-test.result.txt` record separate gates.
- `gpu-virgl.result.txt` records the exact QEMU command, host versions, renderer,
  input ELF/ISO hashes, screenshot hashes and completion/recovery results.
- Per-boot `.serial.log`, `.qemu.log`, `.qmp.log` and `.result.txt` retain actual
  command, device, process, shutdown and comparison evidence.
- `gpu-virgl-render.ppm`, `gpu-virgl-timeout.ppm`,
  `gpu-virgl-recovered.ppm`, `gpu-two-dimensional-render.ppm` and
  `gpu-absent-render.ppm` are actual scanout captures.

## Acceptance boundary

M14.5 is locally accepted only for this bounded hardware render-target clear,
fenced readback and CPU fallback profile. The compositor uses existing CPU
copies to the retained VGA framebuffer. Ordinary window composition remains
software-rendered. No shader draws, guest Mesa/OpenGL/Vulkan API, zero-copy
scanout, general hardware GPU driver, passthrough, speedup, reset-refusal recovery
or remote CI execution is established by this result. CI adds the headless
fallback gate and both GPU feature checks; the hardware gate is explicitly run
on a suitable host.

# M15.3 local GCC feasibility assessment

**English** | [简体中文](../../zh-CN/validation/M15.3.md)

This is a historical local validation record. Later acceptance is tracked in
[current status](../guides/STATUS.md); this documentation update does not rerun the gate.

Recorded 2026-10-24 (Asia/Shanghai), branch `feat/m15-bootstrap`, implementation
base `be17906` with the local changes recorded in the generated report. This
accepts the reproducible assessment in [M15 GCC](../milestones/M15_GCC.md), including its
conclusion that the current profile cannot reconstruct GCC. No GCC compiler
stage, stage2/stage3 bootstrap, Rust/LLVM source build or guest-built kernel is
accepted by this record. Local validation and remote CI are separate.

## Executed assessment

`cargo xtask bootstrap-gcc-test` completed two actual QEMU 8.2.2 q35/TCG boots,
with one CPU, 1 GiB RAM and no NIC. Both boots reached clean ACPI shutdown,
flushed the independent work disk and released the block-device DMA state.
Both read-only `e2fsck -f -n` checks passed. The final result is
`build/logs/bootstrap-gcc.result.json`; it embeds the preparation manifest and
source audit so later preparations cannot change the recorded run's inputs.
Per-boot serial/QEMU/result files use the `bootstrap-gcc-probe` and
`bootstrap-gcc-reboot` prefixes. The captured upstream script output is also
saved as `build/logs/bootstrap-gcc-configure.log`.

The first boot used the inherited guest G++ 11.2.0 to compile `seed.cpp` with
`-std=c++11 -O1`, link a static executable and run its unique-pointer, vector,
initializer-list and lambda checks with the actual result 42. This is a seed
application test, not a rebuilt compiler. Separate compiler invocations for
`gmp.h`, `mpfr.h` and `mpc.h` each returned status 1 and the corresponding
missing-header diagnostic. No rejected object remained, and the previous seed
application still executed successfully after these failures.

The host-built diagnostic separately attempted real `execvp` calls for `sed`,
`awk`, `grep`, `expr`, `tr`, `sort`, `cmp`, `mv` and `ln`. Each child reported
`ENOENT` through a checked pipe and exited 127. The unchanged selected GCC
configure entry point ran through `/linux/sh` with the explicit source path,
build/host/target triples, disabled bootstrap/multilib and C/C++ selection.
It exited 1 during startup. Its six-line log reports only missing `sed` and
`expr`; it did not reach a missing-source-directory rejection. No complete
configure run, arithmetic-library link test or compiler construction occurred.
The startup subset deliberately omits later source/build inputs.

The existing capacity diagnostic again rejected an over-1-MiB persistent
resize while preserving prior bytes, exhausted/recovered descriptors with
`EMFILE`, and exhausted/reaped children with `EAGAIN` before a successful new
fork/wait. The retained seed application then ran again. The independent
second boot executed that persisted application and preserved every workspace
file byte, including upstream inputs, notices, fixtures, the executable,
configure output and the empty shell-created `.lineno` file.

## Source and capacity evidence

Before scanning member metadata, preparation independently checked the seven
official source archive hashes locked in `ports/gcc/inputs.json`; it did not
trust the already extracted M11 trees. Complete release archives total
139,894 regular files and 922,827,305 logical bytes, with 145,684 namespace
nodes as a lower bound and 93 files larger than 1 MiB. GCC alone has 108,258
files, 620,324,686 logical bytes and 65 oversized files. Full archives include
optional tests/docs and unrelated targets; these totals are not a minimal
compiler build dependency closure or measured GCC build demand.

One required ordinary top-level build input, GCC's `Makefile.in`, is
2,145,896 bytes. It alone exceeds the existing writable-file limit. Current
16 MiB/512-inode disk and 2,048-node namespace also cannot import the full
release trees. Additional QEMU RAM does not remove these filesystem limits.
The exact per-release counts, oversized paths, canonical member inventory
hashes and selected-file provenance remain in the embedded source audit.

The source selection and first-party probes fit the existing profile without
changing a disk format, ABI or capacity limit. Resource summaries are sampled
at scheduler boundaries. The first boot includes deliberate exhaustion tests,
so its task/descriptor maxima cannot be attributed to an ordinary compiler
build. Frame deltas include kernel allocations, are not process RSS, and
omit transient allocations inside syscalls. Host wall times include boot and
shutdown; end-of-boot disk use is not transient storage demand. No complete
GCC build was attempted, and its memory/time/storage needs remain unmeasured.

## Regression and source checks

The two Python rejection suites cover the original bzip2 profile and the new
compiler archive/cache workflow. The new suite has six test groups for checksum
changes, unsafe/duplicate/link/special paths, missing or oversized selected
members, exact archive accounting and changed/symlinked publication paths.
`gcc_probe.py --verify` checks the prepared source-only cache without writing it.
Host tests also reject incomplete guest feasibility evidence.

All four final guest/boot gates passed. Exact commands, exit codes and host
durations are retained in `build/logs/m15-gcc-regressions.json`; complete host
output uses `build/logs/m15-gcc-regression-COMMAND.host.log`.

Final formatting, strict Clippy for all CI host packages and the
`bootstrap-metrics` kernel, 190 host unit/doc tests, both Python suites,
source-only verification, 327-file purpose coverage and diff whitespace checks
passed. Exact commands/results and complete output are retained in
`build/logs/m15-gcc-source-checks.json` and `m15-gcc-source-checks.log`.
A separate dangling final-result symlink was rejected before preparation;
its nonexistent target was not created and the accepted report was restored
byte-for-byte. Final implementation/image hashes match the report. Local
links in all 13 changed Markdown documents were checked.

The CI workflow includes the new source rejection suite and GCC assessment in
its existing source-built guest-toolchain job, retaining audit/preparation
manifests and logs. Remote CI was not executed in this local batch. Full OS
`verify`, network/package, Rust/Cargo, GUI and hardware VirGL gates were not
rerun for this isolated host-command/diagnostic change; their earlier records
remain separate. No kernel runtime, capacity, syscall or native ABI changes
were made here.

Before a GCC reconstruction stage, provide functional POSIX build tools,
arithmetic development inputs, a declared source closure, and sufficient
large-file, disk, inode and VFS capacity. Then measure a real sequential build
and prove the resulting compiler can compile and run applications. M15.4 and
M15.5 keep their independent prerequisites; this assessment does not make
compiler source bootstrap a prerequisite for guest kernel reconstruction.

# M16.6: fresh work disk and usable development

**English** | [简体中文](../../zh-CN/validation/M16.6.md)

Implemented and locally accepted 2026-10-27 (Asia/Shanghai) on
`feat/m16-foundation`, base `e963c01`. Depends on the bounded [JBD2 contract](M16.5.md).
This accepts an explicit bzip2 work-volume profile; full M16/remote CI acceptance,
M17 desktop and M18 compiler/image reconstruction remain separately scoped.

## Migration and explicit use

```sh
cargo xtask ext4-journal-image --linux build/disks/new-work.ext4
cargo xtask run --ext4-write --toolchain --disk build/disks/new-work.ext4
# Alternatively copy an existing stopped, clean ext2 image to a new destination:
cargo xtask ext4-migrate build/disks/retained.ext2 build/disks/migrated.ext4
cargo xtask foundation-migrate-test
```

Creation uses e2fsprogs **1.47.0**, a 64 MiB regular file, 4 KiB blocks,
256-byte inodes, 8,192 blocks/group, 4,096 inodes and an 8 MiB internal journal:

```sh
mke2fs -q -t ext4 -b 4096 -I 256 -g 8192 -N 4096 -m 0   -O none,extent,filetype,sparse_super,large_file,has_journal   -J size=8 -E lazy_itable_init=0 -d SOURCE NEW_IMAGE
```

The helper uses create-new and never overwrites an existing image. Paths supplied
through the CLI are regular images under `build/`. No physical block device or
in-place conversion is used. Ordinary/default storage remains ext2. Omit `--linux`
and `--toolchain` for the native ABI profile.

Migration first requires a stopped source passing `e2fsck -fn`, opens it through
an actually readonly file/device wrapper and verifies the immutable ABI marker.
It copies names and bytes in bounded chunks to a newly created destination,
restores permissions and second-resolution atime/mtime/ctime, and compares full
path/type/mode/time/hash inventories after shutdown and readonly remount. Parent
times are restored after copying their children. It hashes the original source
before and after and keeps it available for boot/recovery. The sidecar
`NEW_IMAGE.migration.json` contains the exact inventory and identities. A failed
copy leaves the source intact and its partial destination available for inspection;
there is no implicit promotion or overwrite retry.

## Declared source/tool closure and budgets

The real development load is unchanged upstream **bzip2 1.0.8**, locked by
`ports/bootstrap/inputs.json` (SHA-256
`ab5a03176ee106d3f0fa90e381da478ddae405918153cca248e682cd0c4a2269`).
The preparation tool verifies the official archive, licenses, 21 selected upstream
files and first-party recipe/rejection fixtures. Its complete prepared directory
has 26 files; the migration source adds its ABI marker and four directories,
for 31 inventoried paths. The host copies source bytes and builds the acceptance
supervisor. Only guest GCC/make compile and link the new bzip2 executable.

The inherited, source-built GCC **11.2.0**, make **4.4.1**, binutils and matching
musl sysroot are verified by the existing M11 stage/package inventories.
Build/host are AnovaOS's x86_64 Linux-musl personality; target is static ET_EXEC
x86_64 Linux-musl, sysroot `/tc`. The recipe is
`make -B -f Makefile.anova -j1`, eight C objects and their final link. The acceptance
supervisor and separate storage writer run concurrently with this sequential build.
This uses the inherited compiler; it does not reconstruct GCC/Rust.

Budgets are code constants and are saved **before** comparison in `budgets.json`:

| Measurement/ceiling | Declared budget |
| --- | --- |
| UART input to foreground process execution or compiler-log retrieval | 3,000 ms each |
| UART input to fsync/rename save; clean shutdown response | 5,000 ms each |
| UART input to interrupted build-process-group reaping | 5,000 ms |
| Actual build completion wait | 1,200 seconds |
| Kernel heap / VFS nodes | 16 MiB / 2,048 slots |
| Tasks/threads; descriptors/process | 32 / 32 |

The host measures UART response using `Instant` and the actual serial byte path,
with 5 ms polling; guest IRQ time is not substituted for wall time. Samples are
individual observations under this declared load, not percentile/SLA guarantees.
The existing scheduler-boundary resource sampler records heap/frame/task/fd/VFS
observations and validates their bounds. It misses temporary syscall allocations
and is not peak RSS; stopped-disk use is not transient disk high water. No heap,
task/fd/cache quota increase, SMP or asynchronous block I/O is claimed here.

## Actual acceptance flow

1. Create a clean ext2 source containing the checked build closure, migrate to a
   fresh JBD2 disk and compare all 31 paths/bytes/modes/times. Actually boot the
   retained ext2 source readonly with the same kernel and verify its ABI marker.
2. In the new-disk guest, start real make/GCC and a separate writer repeatedly
   overwriting/fsyncing a 128 KiB file. Wait for an actual GCC command in the log.
   While the builder is still live, accept UART commands that fork/exec BusyBox
   echo, fsync/rename a foreground file and read the real compiler log. Require
   all responses within their budgets; wait for successful compilation/link and
   reap the storage writer before clean shutdown.
3. Boot again, force a rebuild and repeat foreground operations under storage
   pressure. Deliver SIGINT to the build process group, wait for non-success and
   retain the previously working executable. Reap the writer and shut down.
4. Boot again, run the reconstructed bzip2 to compress/decompress official sample
   data, deliberately compile the rejection fixture (requiring the exact compiler
   diagnostic and make status 2), rerun the tool and cleanly shut down.
5. Independently check every stopped image with `e2fsck -fn`. Verify the executable
   hash before/after interruption and rejection, exact decompressed source bytes,
   exact official block-size-1 compressed bytes, the foreground save after reboot,
   unchanged migrated source bytes and the untouched original ext2 image.

The dedicated foreground supervisor is acceptance tooling. General desktop/PTY
editing and the M17 workflow still need their own implementation and acceptance.
Evidence remains under `build/foundation/migration-TIMESTAMP/`: retained source and
work disks, ISO, guest-created ELF, budgets, migration/final inventories, source/
artifact hashes, resource observations and UART logs. CI now invokes the new gates
and uploads the retained evidence; an actual remote result is recorded separately.

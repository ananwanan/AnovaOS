## Executed recipe and retained evidence

The gate ran the complete `bootstrap-test` and `bootstrap-kernel-test` flows
sequentially in each of two rounds. All twelve QEMU 8.2.2 q35/TCG sessions
completed successfully using one CPU and no NIC. Bzip2 sessions used 1 GiB RAM;
kernel sessions used 3 GiB. Each session reached clean ACPI shutdown, successful
disk flush and acknowledged DMA reset. Every stopped disk passed read-only
`e2fsck -f -n`.

The aggregate is `build/logs/bootstrap-repeat.result.json`; the retained
invocation log is `build/logs/m15-repeat-invocation.log`. The unique evidence
directory is `build/bootstrap-repeat/1792852979158547458/`. Each
`round-{1,2}/bzip2/` and `round-{1,2}/kernel/` directory contains its own
component result, prepared/input manifests, initramfs, invocation and complete
serial/compiler logs, stopped work disk, ISO copies, extracted declared outputs
and SHA-256 inventory. Kernel directories also retain `kernel.readelf.txt`
header, section, segment and note listings. The run retains the exact source
snapshot, `source-files.json`, `environment.json` and `comparison.json`.

All four component reports have `clean_build=true`. Each bzip2 disk initially
contained exactly the 26 source/recipe/fixture files, without objects or an
executable; each kernel disk began without a persistent kernel workspace or
Cargo target outputs. Distinct disk paths were checked rather than reusing
the preceding round. The total aggregate host interval was 2,315,907 ms,
including component preparation, compilation, boot/shutdown and archival.

## Functional and failure recovery results

Both bzip2 builds compiled all eight C units in guest GCC processes, linked
the tool and executed compression, decompression and stream integrity checks.
Block-size-1 output matched the official golden fixture; independent host
Python decoding also matched the reference. Invalid input returned status 2.
After reboot, the real C compiler reached the deliberate `#error`, make
returned 2 and the retained compressor still executed successfully. All 37
persisted source/output file hashes were unchanged across that failure/reboot
within each round, and the complete bzip2 file hash maps matched across rounds.

Both kernel builds ran actual guest Cargo/rustc/rust-lld from the locked source
workspace. The host retained their ELF bytes and packaged them through the
path that never rebuilds a kernel. Independent extraction from each ISO matched
that round's retained ELF before boot. New-kernel and recovery boots reported
the exact expected identity and passed native application execution. The real
Rust syntax rejection returned compiler status 1, left no unpublished candidate
and preserved the prior bootable kernel. Each round's 181-file recovery
workspace was unchanged across its final independent reboot.

Capacity probes also verified actual `EFBIG`, `EMFILE` and `EAGAIN` rejection
followed by file, descriptor and child-slot reuse. Exhaustion-probe maxima are
reported separately from the ordinary build observations below.

## Observed metadata and intermediate differences

The comparison retains every report difference. Fresh disk paths, ISO hashes,
host wall times, scheduler sampling and compiler timing differed between
rounds. The bzip2 preparation differences were its ISO hash and work disk path;
the kernel preparation differences were its seed ISO hash and work disk path.
The kernel build identity and initramfs bytes were unchanged. Guest ISO hashes
were `ec047c57664f7b47f2b74b9250a52f80cfde6b914a62fb399303b22cbd7c8b0d`
and `703afb890cfc693e554dcd933257e799e2c1c91b5f043e968296d9cc80de9d0e`;
their extracted kernel bytes were identical. ISO/disk reproducibility is not
claimed. Read-only primary-volume inspection confirmed different ISO creation and
modification times; those descriptors are retained in the diagnostic report.
These metadata differences do not change the declared ELF outputs.

The two kernel recovery workspace inventories differ in ten files: `build.log`,
`target/.rustc_info.json`, five Cargo dependency fingerprint files for
anova-abi/kernel/memory/platform/vfs, generated smoltcp `out/config.rs`, and its
intermediate `.rlib` and `.rmeta`. Raw hashes remain in `comparison.json` and
the copied stopped work disks. Read-only debugfs inspection is retained in
`build/logs/m15-repeat-workspace-analysis.json` with hashes, byte offsets and
the relevant generated contents.

The Rust compiler information parses to equal JSON with differing key order.
Smoltcp's generated file contains the same constant lines in different order;
the locked upstream build script uses a `HashMap` and iterates it directly
when generating constants. Its intermediate library/metadata bytes also differ,
but a complete causal binary diagnosis is not established. The five dependency
fingerprint binaries differ; their cause is not established by this acceptance.
Both complete kernel build logs retain a nonfatal Cargo global-cache advisory
locking warning and different printed durations (7m23s and 7m32s). Each build
still returned 0 and passed explicit artifact/runtime verification. General
cache locking and pruning are not accepted by this result.

Thus acceptance covers the declared eleven bzip2 outputs and final kernel ELF,
plus functional and recovery results. It does not assert equality of every
kernel intermediate, workspace byte, log, filesystem image or ISO.

## Host checks and remaining scope

`cargo xtask test-host` passed 200 tests; retained output is
`build/logs/m15-repeat-final-host.log`. The bzip2/GCC/Rust/kernel source
rejection suites passed 3/6/10/9 tests respectively. Strict xtask and kernel
`bootstrap-metrics` Clippy, formatting, file-purpose coverage, local Markdown
links and diff whitespace checks passed. These checks do not substitute for
the twelve actual guest sessions recorded above. A final independent pass
also verified all 106 retained per-component file hashes against their
`inventory.json` records. The CI workflow runs the aggregate and uploads its
retained evidence; its guest-toolchain timeout is now 120 minutes. This workflow
configuration has not been verified by a remote run.

Host assistance still prepares locked sources and inherited seeds, compiles
the initial kernel/apps and diagnostic drivers, creates work disks, packages
boot images, extracts guest outputs and drives independent verification. Guest
processes construct the selected bzip2 target and final kernel. This gate does
not remove or reassess the separately documented M15.3/M15.4 compiler-source
feasibility blockers, and no GCC/LLVM/rustc/Cargo component was reconstructed.
Guest-only complete image generation, GUI-enabled kernel reconstruction,
native hardware and general reproducibility remain unverified. The Rust
failure fixture is a small rejected source, not a complete failed kernel Cargo
rebuild. Normal shutdown recovery does not establish power-loss recovery for
non-journaled ext2. Two matching final builds establish only this recorded
input/environment comparison, not independence from inherited seeds or
bootstrap from source alone. Remote CI and publication were not verified by
this local acceptance.

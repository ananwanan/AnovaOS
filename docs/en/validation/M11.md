## Guest development and independent disk inspection

`cargo xtask toolchain-test` passed using real UART input on ordinary boots:

1. The runtime probe uses an actual vfork child sharing its parent's bytes.
   The parent is suspended, and its SIGUSR1 handler observes the child's final
   shared value after exec. Failed exec followed by child exit also wakes the
   parent with the correct wait status. It checks private tmpfs snapshots,
   unchanged file offsets, umask, fchmod/stat, unsupported special mode bits
   and the actual 32-descriptor resource bound.
2. The guest editor creates C, C++, Makefile, syntax-error and link-error
   sources. Host inspection later requires their exact bytes, including tabs.
3. Guest GCC compiles and links two C source files. The resulting application
   verifies stdio, malloc/free, argv and file output `guest-C:42`.
4. Guest G++ compiles C++17 with `-pthread`. The application verifies
   string/vector, exception propagation, RAII destruction during unwinding,
   a real std::thread, atomic communication and join.
5. GNU make builds separate objects, reports no work on an unchanged second
   invocation, then recompiles only helper.c after the guest editor changes
   its return value to 43. UART evidence requires one main.o compilation and
   two helper.o compilations, and the rebuilt program writes `guest-C:43`.
6. Actual parser and undefined-symbol linker failures both return status 1.
   The earlier executable still runs, rejected output names are absent, and
   the runtime probe requires compiler temporary-file cleanup.
7. Clean ACPI shutdown is followed by independent ext2 source-byte, ELF,
   executable-mode and SHA-256 inspection and clean `e2fsck -f -n`.
   A second boot executes the saved C and C++ applications and shuts down;
   independent hashes must match across both boots.

## Inherited regression results

- All 13 `cargo xtask verify` scenarios passed their expected gates: normal
  boot exits 33, panic/OOM exits 35, real faults exit 37, and the injected hang
  times out. The OOM gate checks an actual 32 MiB allocation against the new
  16 MiB heap and alloc's default panic handler, not a diagnostic alone.
- Normal boot retains all M9 static/PIE/dynamic-musl, pthread/TLS/futex,
  signals, PTYs, native isolation, frame/heap exhaustion and exact reclamation
  assertions. tmpfs pressure now really exhausts the enlarged heap.
- `terminal-test` passed ordinary serial editing, CRLF/EOF, shell restart,
  dynamic-musl startup, Ctrl+C and fresh-boot tmpfs loss.
- `persistence-test` passed editor/source/ELF retention, actual native
  execution, shutdown/e2fsck, read-only and unknown-feature rejection, and
  real virtio block write/flush failure paths.
- `network-test` passed controlled TCP/UDP/DNS, poll, timeouts, signals,
  descriptor reuse/reclamation and DMA teardown.
- `package-test` passed offline install/upgrade/rollback/remove, reboot and
  retained user data, HTTPS fetch, and exact CA/name/expiry rejection.
- 77 host tests passed, including the expanded startup-vector boundaries,
  private snapshots, preserved offsets, modes/timestamps and strict OOM gate.
- Host Clippy with all targets and warnings denied, native-user Clippy and
  kernel Clippy for qemu-test, double-fault and no-execute passed. Both Rust
  workspace formatting checks and all 189 first-party file-purpose entries
  passed. Python recipes/source locks and the shell entry point parse cleanly.
- `trace-compat` passed for the pinned Linux probes, BusyBox and static/PIE/
  dynamic-musl runtime profiles; host traces remain comparison evidence rather
  than substitutes for guest execution.

The separate CI compiler job constructs the locked tools before running
`toolchain-test`; it uploads evidence and hash inventories rather than toolchain
binaries. Remote GitHub Actions execution is not claimed by this local record.

## Accepted limits

This is offline, static, small C/C++ application development on the declared
musl profile. Exceptions and a standard-library thread are enabled and tested;
arbitrary standard-library and build-system coverage is not implied. Dynamic
application builds, LTO, OpenMP, sanitizers, compiler self-bootstrap and guest
Rust/Cargo are outside M11 acceptance. GCC's optional sysinfo/getrusage and
madvise probes may return ENOSYS; explicit GC parameters support the tested
path without fabricated syscall success.

The system remains one BSP with 32 task slots, eager memory allocation and
fixed resource bounds. ext2 permits 1 MiB files and normal-shutdown persistence;
there is no journal, atomic editor save or power-loss recovery guarantee.
General Linux/glibc, SMP and public source-complete binary toolchain publication
are not claimed. Current limits and ownership details are in M11_TOOLCHAIN.

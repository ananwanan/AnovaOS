# M4 validation record

**English** | [简体中文](../../zh-CN/validation/M4.md)

This document records the isolated native application acceptance run and its
limits. Recorded 2026-10-21 (Asia/Shanghai), branch `feat/m4-user-apps`, based on
`dev` at `3d7d42b0e416b2019d7b55410b87ac7b045e593c` (merged M3). The commit
introducing this file identifies the complete implementation revision.

## Environment and inputs

- x86_64 Ubuntu 24.04.3; pinned Rust/Cargo 1.90.0 with rustfmt and Clippy.
- rustfmt 1.8.0-stable, Clippy 0.1.90; GCC 13.3.0 (`13.3.0-6ubuntu2~24.04`).
- QEMU 8.2.2 (`1:8.2.2+ds-0ubuntu1.18`), q35/TCG, qemu64, 256 MiB, one CPU.
- Host QEMU/xorriso packages were downloaded with apt verification and extracted
  into a temporary private tool directory. Wrapper environment selects their
  libraries, QEMU modules and firmware data; kernel/runner source is unchanged.
- Limine 9.5.0 binary commit, protocol, OVMF 2024.02-2ubuntu0.9 and every input
  hash remain pinned in `boot/dependencies.toml`; `cargo xtask fetch` verified them.
- Application output and its explicit `anova.native.v1` personality/SHA-256 are
  recorded in generated `build/apps/manifest.toml` and copied into the ISO.

## Real user-space results

The passing boot image runs Rust and C ELFs at CPL3. Both print their real
arguments and verify zeroed BSS/SSE2; Rust also checks x87 and default FPU control
state. They use actual SYSCALL instructions and exit 0 and 7 respectively.
The kernel then runs these probe invocations and checks exact results:

| Case | Actual required outcome |
| --- | --- |
| syscalls | Exit 0 after unknown syscall, bad fd/size, null/kernel/noncanonical/overflow/cross-guard pointers, writable cross-page query and DF-on-entry checks |
| timer | Exit 0 after coarse tick changes while Ring 3 receives real IRQs |
| page-fault | User #PF, error 0x4, CR2=0 |
| kernel-read | User #PF, error 0x5, CR2=0xffffffff80000000 |
| kernel-write | User #PF, error 0x7, same supervisor address |
| stack-guard | User #PF, error 0x4, CR2=0x7ffffffdffff |
| invalid-opcode | User #UD, vector 6, error 0 |
| privileged | User CLI causes #GP, vector 13, error 0 |
| bad-rsp | SYSCALL safely enters on trusted stack; return with RSP=-1 is rejected |
| read-only | Actual write into probe text causes user #PF, error 0x7 |
| no-execute | Actual call into non-executable data causes user #PF, error 0x15 |

Every process's private pages/tables/kernel stack are reclaimed before the next
invocation. A partial load limited to three user-page allocations returns OOM
and restores the exact frame count; this is a deliberate allocation-budget
injection, not a claim that this case exhausts all RAM. M3 still performs real
frame exhaustion/recovery. Malformed ELF, PIE, wrong personality and embedded-NUL
arguments are rejected before execution.

Two deliberate copy-site faults exercise read and write fixups at unmapped
0x10000, independently of preflight rejection. These model access-time revocation
after a walk; no concurrent unmapper exists yet. The narrow fixup returns an
error and kernel execution continues. Eight additional Rust app runs verify
fresh BSS/FPU initialization and stable physical-page counts. User IRQ count
is positive and recorded in the boot transcript (it is timing dependent).

The 12 existing negative images still reach their actual injection points:
panic/OOM exit 35, fatal kernel faults exit 37, controlled hang times out. They
never pass merely because an early banner appeared. The boot success image
requires complete M2/M3/M4 stages and QEMU exit 33.

## Artifacts and limitations

`build/logs/` holds serial/QEMU logs and classified results for every case, plus
the normal-image record. CI uploads the same directory. Exact ELF hashes are in
`build/apps/manifest.toml`; artifact hashes below refer to this local run and
are not reproducibility claims because debug paths and ISO timestamps vary.

M4 is one sequential native process at a time. Scheduling, saved FPU task
contexts, simultaneous unmapping, filesystem/input, persistence, Linux ABI,
SMP and physical machines are not implemented or verified. This provides host
built app execution, not GCC/Rust/Cargo running inside the guest. Remote CI
execution is recorded separately from this local evidence.

# M16.5: JBD2 journal and crash recovery

**English** | [简体中文](../../zh-CN/validation/M16.5.md)

Implemented and locally accepted 2026-10-27 (Asia/Shanghai) on
`feat/m16-foundation`, base `e963c01`. This extends [M16.4](M16.4.md), retaining
its non-journal profile and the independent ext2 route. Remote CI is separate.
The format implementation follows the public [JBD2 description](https://www.kernel.org/doc/html/latest/filesystems/ext4/journal.html);
no Linux kernel implementation is incorporated.

## Admitted profile

`ext4-jbd2-v1` keeps the existing 4 KiB blocks, 256-byte inodes, linear directories,
root ownership and strict allocation/namespace audit. It adds COMPAT `has_journal`
(4), internal reserved inode 8, and the INCOMPAT recovery bit (4). External journals,
64-bit/flex/checksummed ext4 metadata, fast/async commits, arbitrary Linux journal
histories, circular/wrapped pending logs and multiple outstanding transactions
are outside this profile. Unsupported combinations fail before recovery writes.

The immutable journal map must fit its inline extent root (at most four extents),
contain 1,024–8,192 4 KiB blocks and have no duplicate/reserved ownership. JBD2 v2
superblocks use big-endian fields, matching UUID, one user and zero abort errno.
Records use CRC32C checksum-v3, 32-bit targets, UUID tags, escaped data, descriptor
and commit checksums. The superblock checksum covers its first 1,024 bytes.
A clean empty mkfs journal without checksums is upgraded at its first transaction;
an active unchecked journal is rejected. Pending logs start at logical block 1.
Transaction sequence wrap to zero is rejected before writing.

Each transaction stages at most 1,024 changed filesystem blocks and must fit its
journal with descriptors/commit. Allocations are fallible, with no allocation in
the device publication phase. The selected new work image has a 2,048-block journal.
A smaller journal can reject a large individual transaction with `NO_MEMORY`;
smaller writes remain available. Existing heap, node/task/fd and mapping bounds
are unchanged. Clean journal images can be mounted readonly; recovery-required
images require the explicit writable route, never hidden readonly replay.

## Durability and recovery contract

This is synchronous **data=journal**, stronger for file overwrites than metadata-only
ordered mode: every staged data and metadata block travels through the log.
One backend operation is the transaction boundary; a multi-syscall application
sequence is not automatically one transaction. Successful mutations have completed
checkpoint/retirement. `fsync`/`sync` flush the mount; rename includes its metadata
commit. Applications can write/fsync a temporary file and rename it for replacement.

1. Persist and flush the ext4 recovery bit, keeping ext4's valid-state bit set.
2. Write/flush the active journal superblock with the transaction sequence.
3. Write descriptors and escaped payloads, then flush the complete log body.
4. Write the checksummed commit and flush it before any home-address change.
5. Write all home blocks and flush the checkpoint.
6. Retire/flush the journal head before its space can be reused.

Any publication write/flush error poisons the live mount and makes sync/shutdown
fail. A failed operation may have committed: after reboot its allowed outcome is
the complete pre-state or complete post-state. It is not reported clean on error.
Successful shutdown clears the ext4 recovery bit only after all orphans are reclaimed
and the journal is retired. Device failure can prevent best-effort marker repair.

Replay first finds the matching checksummed commit. An uncommitted prefix is
ignored. Committed descriptor/payload/commit corruption is rejected; no partially
verified replay is published. The recovered overlay must pass immutable geometry,
unique block ownership, free counters, rooted namespace and link/orphan audits.
The whole checkpoint can be repeated after another crash. A bounded revoke reader
omits revoked targets; the writer needs no revoke records because it fully
checkpoints each transaction before any subsequent block reuse.

Unlink and replacement persist the classic `s_last_orphan`/inode `i_dtime` chain
in the same journal transaction as the namespace change. Open handles/maps retain
their identity while running. On reboot those handles no longer exist, and each
orphan is reclaimed through another journal transaction after the ownership audit.
No live inode is silently leaked or reused through an unrecovered orphan list.

## Actual local acceptance

```sh
cargo xtask foundation-journal-test
cargo test --locked -p anova-storage --test journal
```

Five host tests use real e2fsprogs 1.47.0 images. The matrix runs **1,740** cut
cases across create, overwrite, truncate, rename, unlink and final reclaim:
write-through sectors, volatile cached sectors lost before flush, and a 256-byte
prefix of a failed 512-byte write. Every recovered stopped image passes independent
`e2fsck -fn` and namespace/data checks. Further cases interrupt each replay write/
flush, reject descriptor/payload/commit checksum corruption without writes, exercise
multiple descriptors and magic escaping with 300 data blocks, and compare native
revoke/replay with independent `e2fsck -fy` on an identical failed copy. Twelve
successive real allocator failures cover journal preflight rollback and retry.
These are declared sector/tear models, not arbitrary physical-device fault coverage.

Baselines, exact sector payload/event traces, results and representative original
failed disks are retained in `build/journal-host/`. Any matrix case can be
reconstructed without touching its original disk:

```sh
python3 scripts/reconstruct_journal_cut.py   build/journal-host/matrix/write-baseline.ext4   build/journal-host/matrix/write-events.txt 25 build/disks/cut.ext4 --cache
```

`--tear` reproduces the failed half-sector prefix. Cut indices are zero-based.
The gate also boots an actual one-BSP q35/TCG/OVMF guest with 1 GiB RAM and
virtio-blk: the complete Linux/musl write suite, sync, a persisted marker, forced
QEMU termination, recovery boot, exact metadata checks and clean ACPI shutdown.
The original unclean guest disk is retained before booting the recovered copy.
The write-point pending-commit matrix is host-driven; the guest cut occurs after
sync/checkpoint. Existing M16.4 virtio read/write/flush error gates remain separate.
